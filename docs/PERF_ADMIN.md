# PAMIR — скорость админ-панели

Ветка `perf-admin-panel`. Причина: после волны 2а любая кнопка панели ждала ответа заметно дольше, чем хотелось. Корзина на витрине быстрая, потому что почти не ходит на сервер.

Проверено автотестами на стенде: бэкенд — 341 проверка, витрина в браузере на экране 360 px — 276 проверок. Настоящее время ответа стенд не знает: его показывает только Apps Script. Как посмотреть — раздел «Как замерить на телефоне».

## Что съедало время

Каждое нажатие в панели — отдельный запрос к Apps Script. Внутри запроса медленные не вычисления, а обращения к Google: чтение листа, запись, свойства скрипта, вызов Telegram. Их и было слишком много.

| Что находилось | Где | Сколько лишнего |
|---|---|---|
| Свойства скрипта читались по одному, каждое — отдельным обращением | все запросы | 4–12 обращений на запрос вместо одного |
| Заголовок листа читался отдельно от самого листа | заказы, товары, архив | +1 чтение на запрос |
| Листы «Налаштування» и «Точки» читались при любой смене статуса, хотя нужны только для «Підтверджено» при самовывозе | смена статуса | +2–3 чтения |
| Лист «Точки» читался дважды за один запрос | «Підтверджено» при самовывозе | +1 чтение |
| Лист «Категорії» читался при любой правке товара | сохранение товара, переключатели | +1 чтение |
| После сохранения товара его строка перечитывалась из таблицы | сохранение товара, переключатели | +1 чтение |
| Каждая строка «Журнала» писалась отдельной операцией | сохранение товара, настройки | 3 операции на 3 изменённых поля |
| Сообщения о заказе у админов обновлялись по очереди, по одному вызову Telegram на админа | смена статуса | при двух админах — два вызова подряд вместо одного |
| «Збережено» на кнопке держалось 0,65 с перед возвратом к списку | сохранение товара, категории, админа | +0,35 с ожидания |
| После каждой правки витрина заново запрашивала весь каталог | любые правки товаров | несколько тяжёлых запросов подряд |
| Вкладка загружалась только в момент нажатия | открытие списков | ожидание на каждом первом открытии |

## Что сделано

Бэкенд (`apps-script/Code.gs`):
- свойства скрипта читаются одним обращением на запрос (`scriptProps_`);
- лист читается один раз, заголовок берётся из него же (`orderCols_`, `productCols_` принимают уже прочитанную первую строку);
- сообщение клиенту читает настройки и «Точки», только когда они действительно нужны; «Точки» — один раз за запрос;
- при правке товара «Категорії» читаются, только если меняется категория; ответ собирается из того, что записано, без повторного чтения строки;
- «Журнал»: все строки одного запроса пишутся одной операцией в самом конце (`logBuffer_`, `flushLog_`). Вне запроса (меню, триггеры) — сразу, как раньше;
- сообщения о заказе у всех админов обновляются одной пачкой, параллельно (`tgAll_`). Клиенту сообщение уходит отдельным вызовом — его результат нужен точно;
- замер времени по этапам (`perfStart_`, `perfMark_`, `perfEnd_`), включается свойством `PERF_LOG`.

Витрина (`webapp/app.js`):
- статус заказа на экране меняется сразу; если сервер отказал — возвращается прежний с сообщением;
- заказы подгружаются заранее, пока админ ещё смотрит магазин, «Товари» — пока он смотрит заказы. К нажатию данные уже на месте, а бэкенд «разогрет»;
- уже открытый список показывается сразу и тихо обновляется, если получен больше 30 секунд назад;
- быстрое переключение вкладок больше не оставляет пустой экран;
- «Збережено» на кнопке держится 0,3 с;
- после правок каталог для витрины запрашивается один раз, а не после каждого нажатия.

## Что не менялось (надёжность)

- **Подпись Telegram и права проверяются на сервере при каждом запросе.** Лист «Адміни» читается каждый раз заново, список админов в кэш не кладётся. Если отключить админа прямо в таблице — следующий же его запрос будет отклонён. На это есть тест.
- Цены считает сервер по таблице. Запись в таблицу — под `LockService`. Служебные колонки наружу не уходят.
- Настройки магазина в кэш не кладутся: панель должна показывать и сохранять то, что сейчас в таблице.
- Свойства, которые меняются по схеме «прочитал → изменил → записал» (приглашения админов, ID удалённых товаров), читаются свежими, мимо памяти запроса.
- `worker/worker.js` не менялся. Новых листов и колонок нет.

Стенд считает обращения к Google на одно нажатие и умножает на типичную цену обращения. Это **оценка для сравнения**, а не измерение: настоящие числа будут другими, но соотношение «до/после» показательно. Повторить: `node tests/perf_admin.js путь\к\старому\Code.gs`.

| Сохранить товар (3 поля) | 1480 мс | 615 мс | −58 % |

Чего в этой таблице нет: времени, которое Google тратит на запуск скрипта и пересылку ответа (обычно 0,5–1,5 секунды на запрос). Его код не ускоряет. Поэтому на телефоне выигрыш в секундах будет меньше, чем в процентах выше, а часть выигрыша даёт не скорость сервера, а то, что экран больше не ждёт ответа (статус, предзагрузка списков).

## Как замерить на телефоне

Делается после выкладки. Замер по умолчанию выключен.

1. Таблица → Расширения → Apps Script → слева шестерёнка «Настройки проекта» → внизу «Свойства скрипта» (Script Properties) → «Добавить свойство». Имя `PERF_LOG`, значение `1`. Сохранить.
2. Откройте панель на телефоне и сделайте 5–6 нажатий: открыть «Товари», переключить наличие, сохранить товар, сменить статус заказа.
3. **Самый простой способ.** Внизу экрана панели (только в панели и только у админа) появится серая строка с последними нажатиями, например:
   `status: 1450 мс = сервер 640 (підпис і права 80, таблиця 250, Telegram 280, дія 0, журнал 30) + мережа й Google 810`
   - первое число — сколько прошло от нажатия до ответа;
   - «сервер» — сколько из этого работал наш код, в скобках по этапам;
   - «мережа й Google» — всё остальное: связь и запуск скрипта на стороне Google.
   Пришлите мне скриншот этой строки.
4. **Второй способ, в Apps Script.** В редакторе слева значок «Выполнения» (Executions). Каждая строка — один запрос, в колонке «Длительность» — полное время. Нажмите на строку `doPost`: внутри запись вида `PERF admin.status 640 ms | підпис і права 80 | таблиця 250 | Telegram 280 | дія 0 | журнал 30`.
5. После замера **удалите свойство `PERF_LOG`** (или поставьте `0`). Строка с экрана пропадёт.

Этапы (ветка `perf-admin-marks`, мелкая разбивка; этапы по 0 мс на экране не показываются):
- «властивості скрипта» — первое чтение Script Properties в запросе;
- «підпис HMAC» — проверка подписи Telegram;
- «відкриття таблиці» — первое обращение к таблице в запросе: Google открывает файл. Эту цену платит любой запрос, который работает с таблицей, кто бы ни обратился к ней первым;
- «читання Адміни» — чтение листа «Адміни»; «права» — разбор прав;
- «блокування» — ожидание LockService; «читання Замовлення» / «читання Товари» — чтение листа целиком;
- «запис» — запись ячеек и принудительная запись (flush) вместе с пересчётом формул таблицы; «кеш каталогу» — сброс кэша каталога;
- «підписки» — «Повідомити, коли з’явиться» при возврате товара в наличие; «Telegram» — сообщения админам и клиенту;
- «дія» — остальная работа действия; «журнал» — запись в «Журнал».

Первые замеры с телефона (ночь, версия 14) и разбор, что из этого ускоряется кодом, — в конце файла, раздел «Реальные замеры».

Если «мережа й Google» окажется намного больше, чем «сервер», дальше ускорять код почти нечем — остаётся только то, что экран не ждёт ответа.

## Совместимость старой и новой версий

Витрина и панель обновляются из `main` через GitHub Pages, а `Code.gs` — через New version. Между этими шагами проходит пара минут, и в это время версии смешаны. Оба сочетания проверены прогоном тестов в браузере:

| Сочетание | Как проверено | Результат |
|---|---|---|
| Новая витрина и панель + старый сервер | все тесты витрины этой ветки на `Code.gs` из `main` (`PAMIR_CODE_GS=путь node tests/e2e.js`) | 271 проверка прошла, ошибок нет. Прогон останавливается на единственной проверке, которой нужен новый сервер: строка замеров. Без нового сервера её просто нет |
| Старая витрина и панель + новый сервер | витрина и тесты из `main` на новом `Code.gs` | 259 из 259; старые тесты бэкенда на новом коде — 313 из 313 |

Почему ничего не ломается: запросы и ответы остались прежними — те же действия, те же поля. Новое в ответе только одно необязательное поле `_t` (замеры), и только при `PERF_LOG = 1`; старая панель его не читает. Новых листов, колонок и обязательных свойств нет.

Что будет в переходные минуты:
- **новая панель, старый сервер** — всё работает, статус меняется сразу, списки подгружаются заранее; сам сервер отвечает с прежней скоростью;
- **старая панель, новый сервер** — всё работает как раньше, сервер отвечает быстрее.

Поэтому порядок шагов выкладки не критичен, а прерваться между ними безопасно.

## Кто видит строку с замерами

Только действующий админ и только внутри админ-панели, пока включён `PERF_LOG = 1`.
- Сервер добавляет замеры в ответ только на запросы панели (`admin.*`) и только после проверки подписи и прав. Запросам покупателя (каталог, заказ, корзина, «Мої замовлення») и тем, кому отказано в доступе, замеры не уходят.
- На экране строка показывается только в разделе «Адмін-панель». Когда админ выходит из панели в магазин, строка скрыта.
- У клиентов в магазине её нет никогда. На это есть тесты и на бэкенде, и в браузере.
- В замерах только длительности в миллисекундах и названия этапов, никаких данных.

## Как откатиться

Откат не требует команд и делается в любом порядке — версии совместимы.

**Сервер (бот и магазин).** Таблица → Расширения → Apps Script → Deploy → Manage deployments → карандаш (Edit) у «Telegram webhook…» → в списке **Version** выберите предыдущую версию (ту, что была до «Скорость админ-панели») → Deploy. Новый деплоймент не создавать. Бот и магазин сразу работают на прежнем коде.

**Витрина и панель.** GitHub → вкладка Pull requests → Closed → открыть слитый PR из `perf-admin-panel` → внизу кнопка **Revert** → создастся новый PR → Merge. Витрина вернётся через 1–2 минуты.

**Важно про триггеры.** Ежедневные и ежечасные сообщения клиентам работают не на версии деплоймента, а на последнем сохранённом коде. Выбор предыдущей версии их не откатывает. Если нужно вернуть и их — напишите мне: я отправлю прежний `Code.gs` через `clasp push` (с показом разницы и вашим «ок»), после чего снова New version. В этой ветке код триггеров не менялся по смыслу: изменилось только чтение свойств и запись «Журнала».

**Как понять, что откат нужен:** бот перестал отвечать на `/start`, заказы не приходят админам, в панели ошибки «Не вдалося». В Apps Script → «Выполнения» (Executions) такие запросы помечены красным «Сбой».

## Как включить

Порядок прежний: сначала бэкенд, потом витрина. Оба сочетания версий работают (см. «Совместимость»), так что пауза между шагами безопасна.

1. **Отправить код в Google.** Делает Claude по вашей команде «выкладываем»: показывает `clasp status` и разницу в `Code.gs`, ждёт «ок», потом `clasp push`.
2. **Обновить деплоймент — сразу после шага 1.** Таблица → Расширения → Apps Script → Deploy → Manage deployments → карандаш у «Telegram webhook…» → Version: **New version** → в поле **Description** впишите `Скорость админ-панели` → Deploy. Новый деплоймент не создавать.
3. **Витрина.** GitHub → ветка `perf-admin-panel` → Pull request → Merge в `main`.
   Запомните номер версии, которая была выбрана у деплоймента до шага 2, — она понадобится, если придётся откатываться.
4. `startPolling()` не запускать.

Новых обязательных Script Properties нет. `PERF_LOG` — только на время замера.

## Что проверить на телефоне

1. Открыть магазин обычной кнопкой, подождать 2–3 секунды, нажать значок панели: заказы видны сразу.
2. Перейти на «Товари»: список открывается без «Завантаження…».
3. Заказ → нажать статус: метка статуса меняется мгновенно, кружок на кнопке гаснет чуть позже. Клиенту пришло одно сообщение, у обоих админов сообщение о заказе обновилось.
4. Товар → изменить описание → «Зберегти»: «Збережено» и возврат к списку заметно быстрее.
5. Три переключателя наличия подряд: каждый срабатывает сразу. На витрине изменения видны через секунду-две.
6. Панель → Адміни → «Журнал дій»: правка товара с тремя полями — три строки подряд, порядок правильный.
7. Быстро нажать «Відгуки», потом сразу «Адміни»: открылись «Адміни», пустого экрана нет.

## Решения, принятые по ходу

| Вопрос | Решение |
|---|---|
| Кэш админов в CacheService | Не сделан намеренно. Права перестали бы обновляться мгновенно при правке листа «Адміни» руками (удаление строки в таблице не даёт сигнала скрипту). Вместо этого убраны лишние обращения вокруг: осталось одно чтение небольшого листа |
| Кэш настроек в CacheService | Не сделан: панель должна показывать и сохранять актуальные значения, а в остальных запросах настройки больше не читаются без нужды |
| Кэш каталога | Уже был (5 минут, сбрасывается при правках) — не менялся |
| «Журнал» после ответа | В Apps Script нельзя ответить и продолжить работу. Журнал пишется до ответа, но одной операцией и после снятия блокировки |
| Сообщение клиенту о статусе | Не в пачке, а отдельным вызовом: если пачка не уйдёт целиком, повтор мог бы написать клиенту дважды. Правки сообщений у админов повторять безвредно |
| Оптимистичный статус заказа | Экран меняется сразу; при отказе сервера возвращается прежний статус с сообщением. Вторая кнопка недоступна, пока не ответил сервер |
| Сохранение формы товара | Не оптимистичное: сервер проверяет поля и может отказать, а форма с несохранёнными правками не должна закрываться раньше ответа |
| Прогрев бэкенда | Отдельного «пинга» нет: его роль выполняет предзагрузка заказов — тот же запрос, который всё равно понадобится |
| Предзагрузка заказов | Только у тех, кто уже входил в панель с этого телефона. Права при этом проверяет сервер, как обычно |

## Реальные замеры

Телефон, ночь, версия 14 (возможно, холодный старт):

| Нажатие | Всего | Сервер | Сеть и Google |
|---|---|---|---|
| Смена статуса | 5721 мс | 1998 (подпись и права 603, таблица 645, Telegram 474, журнал 275) | 3723 |
| Открыть «Налаштування» | 3636 мс | 1274 (подпись и права 909, действие 364) | 2362 |
| Открыть «Адміни» | 3589 мс | 1585 (подпись и права 1537, действие 48) | 2004 |
| Сохранить товар | 3920 мс | 1969 (подпись и права 537, таблица 1064, журнал 367) | 1951 |

Контрольный замер с компьютера: пустой запрос к серверу (без таблицы и свойств), 6 раз. Запуск скрипта у Google — 1,05–2,1 с, затем второй сетевой шаг (редирект 302 на выдачу ответа) — 0,4–0,6 с. То есть около 1,5 с уходит, даже когда наш код не делает ничего.

Выводы:
- «Сеть и Google» (2–3,7 с) — больше половины времени. Панель ходит напрямую на `script.google.com`, не через Worker. Кодом `Code.gs` эта часть не ускоряется.
- «Подпись и права» прыгает от 0,5 до 1,5 с при одной и той же работе. Сама проверка подписи — миллисекунды; в этап попадали первое чтение свойств и первое открытие таблицы в запросе. Поэтому этап разбит на мелкие (см. выше): следующий замер покажет, сколько стоит именно чтение листа «Адміни».
- В «Адміни» действие заняло 48 мс после 1537 мс «подписи и прав»: таблица уже была открыта. Значит, дорого первое обращение к таблице, а не лист «Адміни» сам по себе.
