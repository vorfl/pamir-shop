
# Cloudflare Worker PAMIR: что делает и как обновить

Worker делает четыре вещи:
1. Принимает webhook Telegram и пересылает в Apps Script (как раньше).
2. Отдаёт каталог магазина из своего кэша (адрес `/catalog`) — быстро, даже если пришло много людей.
3. Сбрасывает этот кэш, когда Apps Script просит (адрес `/purge`).
4. Раз в 5 минут проверяет Apps Script (только ping) и пишет админам в Telegram, если магазин не отвечает.

Если Worker недоступен, витрина и бот продолжают работать через Apps Script.
Названия пунктов панели Cloudflare иногда меняются; если пункт назван иначе — ищите по смыслу.

## Шаг 1. Вставить новый код
1. Откройте dash.cloudflare.com → Workers & Pages → `pamir-bot`.
2. Нажмите Edit code.
3. Выделите весь старый код (Ctrl+A), удалите и вставьте всё содержимое файла `worker/worker.js` из проекта.
4. Нажмите Deploy. (Это делаете вы сами, после того как Claude скажет, что ветка готова.)

## Шаг 2. Новые переменные (необязательные: без них работает всё, кроме сообщений о сбоях)
Settings → Variables and secrets → Add. Значения вводите сами, в чат их не присылайте.

| Имя | Тип | Что это |
|---|---|---|
| `BOT_TOKEN` | Secret | токен бота @pamir_spices_bot (из BotFather) |
| `ADMIN_CHAT_IDS` | Secret | числовые Telegram-id админов через запятую, например `111,222` |

Уже существующие `GAS_URL` и `WEBHOOK_SECRET` не меняйте. Каждый админ должен хоть раз нажать Start у бота, иначе бот не сможет ему написать.
После добавления переменных нажмите Deploy ещё раз. [ЗАГЛУШКА: проверить название пункта]

## Шаг 3. Расписание (Cron Trigger)
1. Worker `pamir-bot` → Settings → Triggers. [ЗАГЛУШКА: проверить название пункта]
2. Cron Triggers → Add → впишите `*/5 * * * *` → сохраните.

## Шаг 4. Хранилище KV (рекомендуется перед рекламой)
Зачем: без KV кэш каталога живёт только в памяти Worker (у каждого экземпляра свой, он быстро пропадает), а слежение за магазином может молчать, потому что ему негде хранить состояние. Cloudflare Cache API на адресах *.workers.dev документацией не подтверждён: гарантирован только на своих доменах, поэтому на него рассчитывать нельзя.
1. Storage & Databases → KV → Create a namespace, имя `pamir-kv`. [ЗАГЛУШКА: проверить название пункта]
2. Worker `pamir-bot` → Settings → Bindings → Add → KV namespace. [ЗАГЛУШКА: проверить название пункта]
3. Variable name — строго `PAMIR_KV`, namespace — созданный `pamir-kv`. Сохраните и Deploy.

Лимиты бесплатного тарифа KV: 100 000 чтений и 1 000 записей в сутки. Расчёт записей в сутки (при cron раз в 5 минут, 288 запусков):
- Слежение: состояние пишется только при изменении. Без сбоев — 1 запись за всё время (первая), 288 запусков дают 0 записей. Один сбой с восстановлением — около 3 записей (первая ошибка, вторая ошибка, восстановление); при долгом сбое новых записей нет. Итого обычно 0–10 в сутки.
- Каталог: запись при каждом изменении каталога или кнопке «Оновити каталог у магазині зараз» (по числу ваших правок, обычно до 50 в сутки) плюс не чаще раза в 30 минут на каждый работающий экземпляр Worker (до 48 в сутки на экземпляр; при 5 экземплярах до 240).
- Итого примерно 300 записей в сутки в расчёте на нагрузку; запас до 1 000 есть. Это оценка, не замер: число экземпляров Worker под нагрузкой в панели не проверялось.
- Чтений: каждое открытие `/catalog` с «холодным» экземпляром читает KV один раз; 100 000 в сутки хватит с запасом.

Если KV не подключать, всё работает, но менее надёжно (см. выше): слежение молчит, когда состояние хранить негде — так сделано, чтобы не слать лишних сообщений.

Cron на бесплатном тарифе ограничен 10 мс процессорного времени, поэтому он делает только проверку `ping` и работу с маленьким состоянием; каталог cron не трогает. Каталог обновляется только по запросам `/catalog` и `/purge`.

## Шаг 5. Проверка
1. Откройте в браузере `https://<адрес Worker>/catalog`. Должен показаться длинный текст с `"ok":true` и списком `"products"`.
2. Обновите страницу сразу ещё раз — ответ приходит быстрее (это кэш).
3. Откройте адрес Worker без `/catalog` — должно быть «PAMIR bot worker: ok».
4. Бот отвечает на кнопки, как раньше.

## Для разработчика: контракт
- `POST /` (и любой другой путь, кроме `/purge`) + заголовок `X-Telegram-Bot-Api-Secret-Token` = `WEBHOOK_SECRET` → пересылка в `GAS_URL?src=tg&key=...`, ответ `ok`; иначе 403.
- `GET /catalog` → JSON каталога. Только `GAS_URL?action=catalog`, параметры клиента не передаются. Кэш: память изолята → KV (если есть) → Cache API (на workers.dev не подтверждён). Каталог хранится готовой строкой, JSON разбирается один раз при получении от Apps Script. Свежесть 60 с; старее — отдаёт имеющееся и обновляет в фоне; хороший ответ хранится до 24 ч. В кэш попадает только JSON с `ok:true` и массивом `products`. Нет хорошего ответа — 502. Заголовки: `Access-Control-Allow-Origin: *`, `Cache-Control: no-store`.
- `OPTIONS` → 204 с CORS.
- `POST /purge` + заголовок `X-Pamir-Key` = `WEBHOOK_SECRET` → перечитывает каталог, `{"ok":true}`; неверный ключ — 403; Apps Script ответил плохо — 502, старый кэш остаётся.
- cron (каталог не трогает): `GAS_URL?action=ping` (ждёт `ok:true`, таймаут 20 с); 2 ошибки подряд — «Магазин не відповідає» (один раз за сбой); восстановление — «Магазин знову працює»; сообщения одного вида не чаще раза в 30 минут. Без `BOT_TOKEN` или `ADMIN_CHAT_IDS` слежение выключено.
- Запись в KV только при изменении каталога или раз в 30 минут на экземпляр (экономия лимита записей).
- Тест: `node tests/test_worker.js`.
