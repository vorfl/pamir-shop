
# Cloudflare Worker PAMIR: что делает и как обновить

Worker делает пять вещей:
1. Принимает webhook Telegram и пересылает в Apps Script (как раньше).
2. Отдаёт каталог магазина из своего кэша (адрес `/catalog`) — быстро, даже если пришло много людей.
3. Сбрасывает этот кэш, когда Apps Script просит (адрес `/purge`).
4. Раз в 5 минут проверяет Apps Script (только ping) и пишет админам в Telegram, если магазин не отвечает.
5. Хранит справочник городов и отделений Новой пошты и отвечает на подсказки (`/np/cities`, `/np/warehouses`, `/np/status`) без обращения к Новой поште во время заказа. Раздел «Справочник Новой пошты» ниже.

Если Worker недоступен, витрина и бот продолжают работать через Apps Script.
Названия пунктов панели Cloudflare иногда меняются; если пункт назван иначе — ищите по смыслу.

## Что изменилось (ошибки «net catalog»)
Раньше, если у Worker не было сохранённого каталога (новый экземпляр после простоя или сразу после заказа) и Apps Script один раз ответил плохо, покупатель получал ошибку, а следующие 30 секунд Worker вообще не пытался сходить в Apps Script. Теперь:
- Нет сохранённого каталога: Worker делает одну повторную попытку через 0,4 с (только если первая кончилась быстро) и отвечает не позже чем через 4,5 с. Витрина ждёт Worker 6 с, потом сама идёт в Apps Script, так что запас есть.
- 30-секундная пауза теперь только защищает Apps Script, когда есть что отдать из кэша. Без кэша пауза не мешает.
- Много людей одновременно: все делят один запрос к Apps Script, а не шлют по одному.
- Плохой ответ Apps Script (страница ошибки, пустой ответ, обрезанный, ok:false) по-прежнему не сохраняется; пока есть хороший каталог не старше 24 часов, отдаётся он.
- Если Apps Script завис, Worker отвечает ошибкой через 4,5 с, а запрос дорабатывает в фоне и наполняет кэш.
Записей KV стало не больше, чем было. Вам нужно один раз заново вставить `worker/worker.js` в Cloudflare (Шаг 1) и нажать Deploy; новых переменных нет.

## Насколько старым может быть каталог у покупателя
- Обычно не старше 5 минут. Если сохранённой копии больше 5 минут (например, после правки таблицы руками или заказа), Worker сначала просит свежий каталог у Apps Script и ждёт не больше 4,5 с.
- Если Apps Script не ответил вовремя или ответил плохо, покупатель получает старую копию, но не старше 24 часов. В этом случае заказы всё равно не пройдут, пока Apps Script недоступен.
- После такого сбоя 30 секунд Worker не ждёт Apps Script и отдаёт старую копию сразу, потом пробует снова.
- Кнопка «Оновити каталог» по-прежнему обновляет сразу.
- Заголовок ответа `X-Pamir-Cache`: HIT (свежий), STALE (до 5 минут), REFRESHED (старая копия заменена новой), EXPIRED (старая копия, Apps Script не ответил), MISS (копии не было). Витрина его не читает.
- Записей KV стало не больше.
Вам нужно заново вставить `worker/worker.js` в Cloudflare (Шаг 1) и нажать Deploy; новых переменных нет.

## Шаг 1. Вставить новый код
1. Откройте dash.cloudflare.com → Workers & Pages → `pamir-bot`.
2. Нажмите Edit code.
3. Выделите весь старый код (Ctrl+A), удалите и вставьте всё содержимое файла `worker/worker.js` из проекта.
4. Нажмите Deploy. (Это делаете вы сами, после того как Claude скажет, что ветка готова.)

## Шаг 2. Новые переменные (необязательные: без них работает всё, кроме сообщений о сбоях)
Settings → Variables and secrets → Add. Значения вводите сами, в чат их не присылайте.

| Имя | Тип | Что это |
|---|---|---|
| `BOT_TOKEN` | Secret | токен бота @pamir_spices_bot (из BotFather) |
| `ADMIN_CHAT_IDS` | Secret | числовые Telegram-id админов через запятую, например `111,222` |

Уже существующие `GAS_URL` и `WEBHOOK_SECRET` не меняйте. Каждый админ должен хоть раз нажать Start у бота, иначе бот не сможет ему написать.
После добавления переменных нажмите Deploy ещё раз. [ЗАГЛУШКА: проверить название пункта]

## Шаг 3. Расписание (Cron Trigger)
1. Worker `pamir-bot` → Settings → Triggers. [ЗАГЛУШКА: проверить название пункта]
2. Cron Triggers → Add → впишите `*/5 * * * *` → сохраните.

## Шаг 4. Хранилище KV (рекомендуется перед рекламой)
Зачем: без KV кэш каталога живёт только в памяти Worker (у каждого экземпляра свой, он быстро пропадает), а слежение за магазином может молчать, потому что ему негде хранить состояние. Cloudflare Cache API на адресах *.workers.dev документацией не подтверждён: гарантирован только на своих доменах, поэтому на него рассчитывать нельзя.
1. Storage & Databases → KV → Create a namespace, имя `pamir-kv`. [ЗАГЛУШКА: проверить название пункта]
2. Worker `pamir-bot` → Settings → Bindings → Add → KV namespace. [ЗАГЛУШКА: проверить название пункта]
3. Variable name — строго `PAMIR_KV`, namespace — созданный `pamir-kv`. Сохраните и Deploy.

## Лимиты бесплатного тарифа (простыми словами)
KV: 100 000 чтений и 1 000 записей в сутки. Cron-триггеров на бесплатном аккаунте 5; Worker использует 1 (`*/5 * * * *`, 288 запусков в сутки). Файла wrangler.toml в проекте нет, расписание задаётся в панели.

Записи KV в сутки (раньше -> теперь):
- Каталог. Раньше: при реальном изменении и ещё раз в 30 минут, то есть до 48 + число правок (около 100 в сутки в оценке). Теперь: только если изменился сам каталог (сравнивается отпечаток SHA-256 без поля `updated`; он лежит в metadata рядом со значением, отдельной записи нет) и ещё 1-2 раза в сутки плановое обновление, чтобы запись не истекла. Если два экземпляра Worker заметили одно изменение, второй видит чужую запись и не пишет. Обычный день без правок: 2 записи. Каждая правка товаров: +1.
- Свежесть «60 секунд» держится в памяти и в Cache API, KV для неё не нужен.
- Кнопка «Оновити каталог»: 1 запись, если каталог изменился, и 0, если нет.
- Слежение (cron): состояние пишется только при смене (первая ошибка, вторая ошибка, восстановление). Без сбоев 0 записей в сутки (одна запись раз в 7 дней, когда состояние истекает), долгий сбой около 3 записей.
- Пауза после сбоя Apps Script в KV не пишется.
- Итого обычный день: 2-5 записей; при 50 правках каталога около 55. До лимита 1 000 запас в десятки раз.

Чтения KV в сутки: сначала читается Cache API, KV только запасной слой. Чтение KV бывает, когда экземпляр Worker «холодный» и в Cache API пусто (на адресе *.workers.dev Cache API может не работать), плюс 288 чтений состояния слежения от cron. Худший случай (Cache API не работает): не больше одного чтения на открытие магазина и не больше одного в минуту на тёплый экземпляр. При 1 000 открытий в сутки: до 1 300 чтений; при 10 000 открытий: до 10 300. Лимит 100 000, запас большой.
Всё это расчёт по коду и тестам с поддельным KV, не замер в Cloudflare.

Если KV не подключать, всё работает, но менее надёжно (см. выше): слежение молчит, когда состояние хранить негде — так сделано, чтобы не слать лишних сообщений.

Cron на бесплатном тарифе ограничен 10 мс процессорного времени (документация Cloudflare, Limits: CPU time per Cron Trigger), поэтому каждый запуск делает мало: проверку `ping`, маленькое состояние и один небольшой шаг загрузки справочника НП (см. ниже); каталог cron не трогает. Каталог обновляется только по запросам `/catalog` и `/purge`.

## Шаг 5. Проверка
1. Откройте в браузере `https://<адрес Worker>/catalog`. Должен показаться длинный текст с `"ok":true` и списком `"products"`.
2. Обновите страницу сразу ещё раз — ответ приходит быстрее (это кэш).
3. Откройте адрес Worker без `/catalog` — должно быть «PAMIR bot worker: ok».
4. Бот отвечает на кнопки, как раньше.

## Справочник Новой пошты (подсказки города и отделения из Worker)
Зачем: подсказки при оформлении заказа больше не ходят в Новую пошту (НП) через Apps Script. Worker сам раз в сутки медленно, маленькими шагами загружает справочник в KV и отвечает мгновенно. Если Worker недоступен, справочник не загружен или данные старше 7 суток, Worker отвечает `{"ok":false,"error":"nodata"}`, и витрина идёт старым путём через Apps Script. Стоимость доставки, создание накладных и статусы по-прежнему делает Apps Script.

### Что нужно сделать (один раз)
1. Ключ API НП возьмите в личном кабинете НП (раздел с API-ключом). [ЗАГЛУШКА: точное название раздела в кабинете НП не проверено.] Тот же ключ, что уже лежит в Script Properties таблицы (`NP_API_KEY`), подойдёт.
2. dash.cloudflare.com → Workers & Pages → `pamir-bot` → Settings → Variables and secrets → Add. [ЗАГЛУШКА: проверить названия пунктов]
3. Type: Secret. Variable name: строго `NP_API_KEY`. Value: ваш ключ НП (вводите сами, в чат не присылайте). Нажмите Deploy.
4. KV `PAMIR_KV` уже должен быть подключён (Шаг 4 выше). Без него справочник не работает.
5. Вставьте новый `worker/worker.js` заново (Шаг 1: Edit code → Ctrl+A → вставить → Deploy). Расписание `*/5 * * * *` остаётся то же, новых триггеров не нужно.
6. Необязательные числа (если не добавлять, всё работает): `NP_REFRESH_HOURS` (как часто обновлять справочник, по умолчанию 24, допустимо 12-168), `NP_PAGE_SIZE` (записей в запросе к НП, по умолчанию 150), `NP_PAGES_PER_RUN` (запросов за запуск, по умолчанию 2), `NP_ASM_KB` (сколько КБ собирать за запуск, по умолчанию 350). Тип Text. Меняйте только по просьбе разработчика.

### Как посмотреть, загрузился ли справочник
Откройте в браузере `https://<адрес Worker>/np/status`. Это текст JSON без секретов:
- `key: true`, `kv: true` — ключ и хранилище подключены (значения не показываются). `false` — шаг выше пропущен.
- `published` — готовый справочник: `at` (когда загружен), `cities`, `warehouses`, `fresh` (true — моложе 7 суток). `null` — первой загрузки ещё не было.
- `loading` — что делает загрузка сейчас: `stage` (`fetch` — берёт данные у НП, `asm` — раскладывает, `merge` — завершает, `idle` — отдыхает до следующих суток), `percent`, `pausedUntil` (если НП сказала «слишком часто», Worker ждёт сам), `lastProblem` (`limit`, `empty`, `api`, `net`, `incomplete`, `lost`, `stuck`), `writesToday`.

### Сколько ждать первой загрузки
Worker берёт не больше 2 страниц у НП за запуск раз в 5 минут. При 30 000 отделений (число оценочное, точного у меня нет) это около 100 запусков загрузки и 10-12 запусков сборки, то есть примерно 9-10 часов. Сразу после Deploy процент в `/np/status` начнёт расти. Это намеренно медленно: так нагрузка на НП и процессор Cloudflare минимальны. Пока справочник не готов, всё работает через Apps Script как раньше. Дальше справочник обновляется раз в сутки; новое поколение подменяет старое одним действием только когда загружено полностью, неполное не публикуется.

### Если что-то пошло не так
- `lastProblem: limit` — НП ограничила частоту; Worker сам ждёт 15 минут, затем 30, 60, 120 и продолжает с того же места.
- `lastProblem: api` — НП отклонила запрос (чаще всего неверный или просроченный ключ): проверьте секрет `NP_API_KEY`. Worker повторяет раз в час.
- Процент долго стоит на одном числе, стадия `asm`, `pausedUntil` пуст — признак того, что сборка превышает 10 мс процессора (в Cloudflare: Metrics → ошибки «Exceeded CPU Time Limits»). Сообщите разработчику: нужно уменьшить `NP_ASM_KB` или сменить схему. Это не проверено на настоящем Cloudflare.
- Ошибки справочника не ломают каталог, заказы и слежение: витрина просто использует Apps Script.

| Записи KV за сутки: слежение | 0-3 | |

Раз в сутки укладывается в лимит записей KV с запасом, поэтому по умолчанию именно так. Реже можно: `NP_REFRESH_HOURS`.

### Для разработчика: формат ответов (как у np.city и np.whall)
- `GET /np/cities?q=<от 2 до 40 символов>` → `{"ok":true,"list":[{"n":"м. Дніпро, Дніпропетровська обл.","s":"Дніпро","ref":"<CityRef>"}]}`, не больше 10. Регистр, ё/е, і/и/ї, є/е, апострофы не важны; русское и украинское название ищутся вместе. Порядок: начало названия, затем начало слова, затем вхождение; внутри группы города выше сёл, затем по числу отделений. Короче 2 или длиннее 40 символов, либо без совпадений: `{"ok":true,"list":[]}`.
- `GET /np/warehouses?city=<CityRef>` → `{"ok":true,"list":[[номер,"короткий адрес","w"|"p"],…]}` (`p` — почтомат), по возрастанию номера; при равном номере отделение раньше почтомата. Необязательно `q` (номер или часть адреса, не больше 12 ответов) и `t=locker|branch`. Витрина фильтрует список сама.
- `city` не UUID → HTTP 400 `{"ok":false,"error":"bad_city"}`. Нет данных (нет ключа или KV, справочник не загружен или старше 7 суток, города нет) → HTTP 200 `{"ok":false,"error":"nodata"}`, `Cache-Control: no-store`; витрина идёт через Apps Script.
- Успешные ответы: `Cache-Control: public, max-age=600`, CORS `*`.
- `GET /np/status` — см. выше, `no-store`.
- Хранение: `np:st` (состояние конвейера, около 300 байт), `np:r:<поколение>:<k>` (сырые куски, живут 3 суток), `np:g:<поколение>:0..31` (корзины по хэшу CityRef: строка на город с готовым JSON и готовый JSON списка отделений города), `np:g:<поколение>:c` (индекс городов), `np:meta` (указатель на текущее поколение; пишется последним, одной записью). Старые поколения не удаляются (удаление считается записью), сами пропадают через 8 суток.
- Схема и ограничения: загрузка идёт `getWarehouses` без `CityRef`, постранично. Города берутся из самих записей отделений (поля `CityRef`, `CityDescription`, `CityDescriptionRu`, `SettlementAreaDescription`, `SettlementTypeDescription`, `SettlementRegionsDescription`), поэтому в индексе только города с отделениями. Названия полей взяты из открытых библиотек, а не из официальной документации НП: если область или тип населённого пункта не придут, ответ будет без «обл.» и «м.», остальное работает. Русские адреса отделений не хранятся (витрина ищет по украинскому короткому адресу, как раньше).

## Для разработчика: контракт
- `POST /` (и любой другой путь, кроме `/purge`) + заголовок `X-Telegram-Bot-Api-Secret-Token` = `WEBHOOK_SECRET` → пересылка в `GAS_URL?src=tg&key=...`, ответ `ok`; иначе 403.
- `GET /catalog` → JSON каталога. Только `GAS_URL?action=catalog`, параметры клиента не передаются. Кэш: память изолята → KV (если есть) → Cache API (на workers.dev не подтверждён). Каталог хранится готовой строкой, JSON разбирается один раз при получении от Apps Script. Свежесть 60 с; старее — отдаёт имеющееся и обновляет в фоне; хороший ответ хранится до 24 ч. В кэш попадает только JSON с `ok:true` и массивом `products`. Нет хорошего ответа — холодный запрос идёт в Apps Script (одновременные делят один обмен), при сбое за первые 3 с — один повтор через 0,4 с; ответ не позже 4,5 с, иначе 502 (обмен дорабатывает в фоне). После сбоя Apps Script 30 секунд фоновых обновлений нет, пока есть что отдать (прошлый хороший ответ); без кэша пауза не действует. Заголовки: `Access-Control-Allow-Origin: *`, `Cache-Control: no-store`.
- `OPTIONS` → 204 с CORS.
- `POST /purge` + заголовок `X-Pamir-Key` = `WEBHOOK_SECRET` → сразу `{"ok":true}`, перечитывание каталога идёт в фоне (не чаще раза в 5 с); неверный ключ — 403 без обращения к Apps Script; если Apps Script ответит плохо, старый кэш остаётся.
